# Golden vectors — cross-language reproducibility

`golden.json` is a deterministic set of test vectors emitted by the JavaScript
reference implementation. It exists to prove one claim that Node alone cannot:
that an **independent** implementation, in another language, reproduces this
extension's canonicalization and digests **byte-for-byte** and can verify a
JS-signed token. `python/verify_vectors.py` is that independent implementation.

## What the vectors contain

`golden.json` is generated by `scripts/gen-golden.mjs`, which reuses the
reference primitives (`canonicalize` from `scripts/jcs.mjs`;
`cardSigningPayload` from `scripts/presence.mjs`; `digestPart`, `cardDigest`
from `scripts/sign-message.mjs`). Fields:

| Field | Meaning |
|-------|---------|
| `input_card` | Fixed Agent Card exercising every §8.4.1 presence class: REQUIRED kept at default (`description: ""`, `skills: []`), EXPLICIT optional kept at default (`streaming: false`) and non-default (`pushNotifications: true`), IMPLICIT dropped at default (`tenant: ""`, `required: false`, empty skill mode lists, empty `securitySchemes`), Struct passthrough (`extensions[].params`), `signatures` removed, and an unknown vendor field (`x-flocker`) kept verbatim. Includes non-ASCII code points to exercise UTF-8 handling. |
| `input_parts` | Fixed parts covering all four `src` kinds: `text` (incl. non-ASCII), `raw` (strict RFC 4648 base64), `data` (JCS of the value), `url` (with `mediaType` + `filename`). |
| `card_payload_canonical` | The presence-processed card, JCS-canonicalized (the exact string hashed for `card_digest`). |
| `card_digest` | `{ alg, value }` per §7.1. |
| `parts[]` | For each part, its `input` and the resulting `digest` entry (§7.2). |
| `token` | A compact ES256 JWS signed with the mock key over fixed claims. |
| `token_header`, `token_claims` | The header and claims the token was signed over. |
| `public_jwk` | The mock **public** JWK (public key only — safe to embed). No private scalar is present, so the Python verifier needs no access to `keys/`. |

The digests and canonical payload are fully deterministic. ES256 signing is
internally randomized, so re-running `gen-golden.mjs` changes only the token's
signature bytes — it still verifies against `public_jwk`, which is what the
cross-check asserts.

## Regenerate the vectors (JS side)

```bash
node scripts/gen-golden.mjs
```

Requires `keys/mock-signing-key.jwk.json` (committed as a mock test fixture —
regenerating it with `generate-keys.mjs` changes the signed `token`, though
digests stay byte-identical). Prints the canonical payload, `card_digest`,
each part digest, and the token.

## Cross-check (Python side)

The Python verifier is an independent implementation:

- JCS via the **`rfc8785`** PyPI package (a vetted RFC 8785 library — not a
  hand-rolled canonicalizer),
- ES256 verification via **`cryptography`**,
- the §8.4.1 presence rules ported directly from the normative Appendix A
  field-behavior table,
- the `card_digest` and the domain-separated per-part digest construction
  (`UTF8(JCS(header)) || 0x00 || content-bytes`, with per-`src` content-byte
  rules: text/url exact UTF-8, raw strict RFC 4648 base64 decode, data = JCS of
  the value).

It loads `golden.json` and asserts byte-for-byte equality of (a) the canonical
card payload string, (b) `card_digest`, (c) every part digest, then verifies the
embedded token's ES256 signature against the embedded public JWK.

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r python/requirements.txt
python python/verify_vectors.py
```

Expected output ends with:

```
ALL CHECKS PASSED — Python reproduced the canonical payload, every digest, and verified the JS-signed token.
```

This is a **separate, documented step**: it is intentionally *not* wired into
`npm test`, because it requires a Python toolchain.

## Result

Verified with `rfc8785` 0.1.4 and `cryptography` 49.0.0 on CPython 3.12: the
Python implementation reproduces the canonical card payload, the `card_digest`,
and all four per-part digests byte-for-byte, and verifies the JS-signed ES256
token — with no shared code between the two implementations and JCS supplied by
an independent library on each side.
